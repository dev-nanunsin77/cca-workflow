# cca-workflow v0.2 설계 — 데이터 기반 워크플로

## 1. 목표
v0.1 의 고정 흐름(pm → tests → 구현 → test/debug → review)을 **코드에서 데이터로** 꺼내,
요청 종류에 맞는 흐름을 고르고, 역할과 백엔드를 분리하고, 실행 상태를 남긴다.

v0.1 의 자산은 그대로 유지한다: Node 단일 파일·무의존성, Claude Code 세션이 루프를 구동하고
직접 구현, 테스트 선작성 + 해시 잠금, dispute, 읽기 전용 디버거, 언어 프리셋.

### 비목표
- 에이전트 간 통신(mailbox, 대화방, 답장 대기). 모든 호출은 지금처럼 단방향 요청 → 결과.
- LangGraph·Python·로컬 LLM 도입. 상태 머신은 cca.mjs 안에서 직접 구현한다.
- LLM 이 실행 계획(DAG)을 자유 생성하는 방식. 흐름은 **미리 정의된 preset 중에서 고른다.**
- 병렬 실행. 모든 step 은 순차 실행한다.

## 2. 핵심 개념

### 2.1 Workflow (`.cca/workflows/<name>.json`)
step 목록과 전이 규칙. 의존성을 늘리지 않기 위해 YAML 대신 JSON 을 쓴다.

```json
{
  "name": "feature-tdd",
  "description": "새 기능: 기획 → 테스트 선작성 → 구현 → 검증 → 리뷰",
  "steps": [
    { "id": "plan",   "kind": "agent", "task": "plan" },
    { "id": "tests",  "kind": "agent", "task": "write_tests", "expect": "red" },
    { "id": "impl",   "kind": "coder", "instruction": "plan 의 계약대로 구현만 작성" },
    { "id": "test",   "kind": "test",
      "on": { "fail": "analyze", "pass": "review" } },
    { "id": "analyze","kind": "agent", "task": "analyze_failure",
      "on": { "design": "plan", "default": "impl" }, "maxVisits": 5 },
    { "id": "review", "kind": "agent", "task": "review",
      "on": { "critical": "impl", "major": "impl", "default": "done" } }
  ]
}
```

- `on` 이 없으면 다음 step 으로 진행한다. `done` 은 종료.
- `maxVisits` 를 넘기면 run 이 `escalated` 상태로 멈추고 사람에게 보고한다.
- 되돌아가는 전이(예: `analyze → plan`)도 같은 규칙으로 표현한다.

### 2.2 Step 종류
| kind | 실행 주체 | 결과(전이 키) |
|------|-----------|---------------|
| `agent` | 역할에 매핑된 외부 CLI (codex/agy) | task 별: `ok`, severity(`critical`/`major`/`minor`/`none`), `design` 등 |
| `test` | 언어 프리셋의 테스트 명령 (잠금 검증 포함) | `pass` / `fail` / `tampered` |
| `coder` | Claude Code 세션 (현재 대화) | Claude 가 `next` 를 호출하면 `ok` |

**task** 는 프롬프트, 출력 스키마, 결과 해석을 묶은 내장 단위다. v0.1 하위 명령이 그대로 옮겨온다:
`plan`(구 pm), `write_tests`(구 tests), `analyze_failure`(구 debug fail), `review`(구 debug review),
`judge_dispute`(구 dispute). 새 task 를 추가하려면 cca.mjs 의 task 표에 항목 하나를 추가한다.

### 2.3 역할과 백엔드 (`.cca/roles.json`)
```json
{
  "roles": {
    "pm":       { "backends": ["codex", "agy"] },
    "tester":   { "backends": ["agy", "codex"] },
    "debugger": { "backends": ["agy", "codex"] },
    "reviewer": { "backends": ["agy", "codex"] },
    "judge":    { "backends": ["agy", "codex"] }
  },
  "tasks": {
    "plan": "pm", "write_tests": "tester", "analyze_failure": "debugger",
    "review": "reviewer", "judge_dispute": "judge"
  }
}
```
- backend adapter 인터페이스: `invoke(backend, { promptFile, schema, effort, readOnly }) → { ok, json|text, limitHit, elapsedMs }`.
- 앞의 backend 가 **사용량 한도·미설치·타임아웃**이면 다음 backend 로 넘어가고 그 사실을 run 기록에 남긴다.
- 모든 agent step 은 해당 CLI 의 가장 제한적인 모드(읽기 전용)로 실행한다. 파일 쓰기는 cca 가 JSON 결과를 받아 수행한다.

### 2.4 Run 상태 (`.ai/run.json`)
```json
{
  "id": "20261123-153000-csv-parser",
  "workflow": "feature-tdd",
  "requirement": "...",
  "reason": "새 기능 요청이고 테스트로 검증 가능",
  "status": "running | waiting_coder | done | escalated | failed",
  "current": "impl",
  "visits": { "analyze": 2 },
  "disputes": [{ "verdict": "reject", "reason": "..." }],
  "history": [
    { "step": "plan", "backend": "codex", "result": "ok", "elapsedMs": 41000, "at": "..." }
  ]
}
```
- 중단 후 `resume` 은 `current` 부터 다시 시작한다.
- 완료 보고(브랜치, 소요 시간, 디버그 횟수, dispute 결과, 최종 severity)는 이 파일로 생성한다.

## 3. 실행 모델
Claude Code 가 루프를 돌리는 구조는 유지하되, **다음 step 결정은 cca 가 한다.**

```
/cca-go [--flow <name>] <요구사항>
  └ Claude: workflow 선택(미지정 시 §4 규칙) → node .cca/cca.mjs run <flow> "<요구사항>" --reason "..."
      └ cca: agent/test step 을 자동 실행하며 전이 → coder step 에서 멈춤
         출력:  ACTION: implement / STEP: impl / CONTEXT: .ai/run.json, docs/plan.md
  └ Claude: 구현 → node .cca/cca.mjs next
      └ cca: test → (fail) analyze → coder 로 복귀 …  → done | escalated
```

- `next`: 현재 coder step 을 완료 처리하고 다음 coder step 이나 종료까지 자동 진행.
- `dispute "<이의>"`: coder step 에서만 허용. accept 면 테스트 교체 + 재잠금.
- `status`: 현재 run 요약. `resume`: 중단된 run 재개. `abort`: run 종료.
- 기존 단일 명령(`pm`, `tests`, `test`, `debug`, `dispute`, `lang`)은 수동 사용과 디버깅을 위해 유지한다.

## 4. Workflow 선택
| preset | 쓰는 경우 | 흐름 |
|--------|-----------|------|
| `feature-tdd` | 새 기능, 테스트로 검증 가능 | v0.1 과 동일 |
| `bugfix` | 재현 가능한 버그 | 재현 테스트 작성(red) → 수정 → test → 리뷰 |
| `refactor` | 동작 변경 없는 구조 개선 | 기존 테스트 green 확인·잠금 → 수정 → test → 리뷰 |
| `quick` | 작은 수정(설정, 오타, 한두 줄) | 수정 → test(있으면) → 리뷰(low) |
| `review-only` | 이미 있는 변경 검토 | 리뷰 |

- 사용자가 `--flow` 로 지정하면 그대로 쓴다.
- 미지정이면 Claude 가 위 표로 고르고 `--reason` 에 근거를 남긴다. 애매하면 `feature-tdd`.

## 5. 마일스톤
각 단계는 별도 커밋. 회귀 확인용 요구사항은 v0.1 에서 실제로 돌려 본 CSV 파서(`cca/csv-parser`)를 쓴다.

1. **동작 동일 리팩터링**: step 실행기 + `feature-tdd.json` + `run`/`next`/`status`. 기존 하위 명령은 task 를 호출하는 얇은 래퍼가 된다.
   - 수용 기준: `feature-tdd` 로 CSV 파서를 끝까지 실행해 v0.1 과 같은 산출물(plan, 잠긴 테스트, debug/review 결과)이 나온다.
   - 외부 CLI 를 부르지 않는 전이 로직은 가짜 backend 로 단위 테스트한다.
2. **역할·백엔드 분리**: `roles.json`, adapter 통일, 사용량 한도 감지와 fallback.
3. **실행 상태 활용**: `resume`/`abort`, run.json 기반 완료 보고.
4. **preset 추가**: `bugfix`, `refactor`, `quick`, `review-only` + cca-go 의 선택 규칙.
5. **되돌아가기**: `analyze_failure` 스키마에 `root_cause_kind`(`impl`/`test`/`design`) 추가, `design` 이면 plan 수정으로 복귀(인터페이스 계약이 바뀌면 사람 확인).

## 6. 미결정 사항
- codex·agy 의 사용량 한도 응답 형태(exit code·출력 패턴) — 2단계에서 실측.
- `refactor` 에서 "기존 테스트" 범위를 정하는 방법(전체 잠금 vs 지정 파일).
- coder step 이 테스트가 아닌 산출물(문서 등)을 낼 때의 검증 방법.
